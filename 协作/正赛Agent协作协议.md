# 正赛 A B C Agent 协作协议

2026-09-21，依据用户指定的分工及补充澄清制定。A、B、C 是三位真人各自操作的三个 Agent，不是 A 自动启动的三个子 Agent。本会话为 A 端。正式赛题开始后按本协议执行；当前只固化协作安排，不创建虚构的求解、派稿或验收记录。

## 职责和交付

| Agent | 职责 | 交付与边界 |
| --- | --- | --- |
| A 主控与求解 | 读题、问题分析、数据审计、建模、推导、代码编写、求解、结果检查、图表证据、逐问派稿；最后全面审核并编写整篇论文 | 维护正式题意、模型、代码和结果；指定 B 的思路与格式；解决数学或计算问题；统一全篇，不仅拼接章节 |
| B 章节作者 | 接收 A 的逐问交付，写对应章节；接收 C 的意见逐项修订 | 输出可直接纳入论文的章节及引用、图表清单；不能自行改模型、重算或补造结果 |
| C 章节格式审查 | 审查 B 的章节源稿及实际渲染页面，将问题反馈给 B；修订后复查 | 输出带位置、原因和修改要求的审查记录；不直接改写 B 的章节，不替代 A 的数学与结果审核 |

O/M/E/W 保留为统筹、建模、编程和写作职责占位，由三位操作者按实际安排兼任。A/B/C 表示各真人操作的工作端；具体姓名与职责兼任关系尚未登记。AI 审查通过只表示对应范围完成审查，不代表操作者已作人工复核、阶段通过或正式提交授权。

## 每问完成就交接

1. A 完成本问分析、模型、实际求解和适合该题型的检查。理论题以推导、证明或构造及必要核验作为交付，不强制制造数值实验。
2. A 准备带版本的写作任务文件，说明核心论证和格式要求；A 操作者通过仓库交接给 B 操作者，由后者在自己的 Agent 中启动写作，A 可继续处理后续问题。
3. B 在自己的 clone/worktree 中完成章节和编译预览，提交源稿、图表引用及待澄清项。B 操作者交给 C 操作者，由 C 在自己的 Agent 中审查源稿与渲染页面。
4. C 将审查记录交回 B，并供 A 查阅。B 操作者启动修订，逐项说明处理位置；C 操作者启动复查，直到问题关闭，或明确列出尚未解决的阻塞。这里的“交给”指真实文件和版本交接，不表示 Agent 已自动收到消息或开始运行。
5. 格式问题由 B 修；题意、模型、数值、证明或数据不足由 A 修。B、C 不得通过改变结论或删除失败结果来消除审查问题。
6. 全部问题章节完成后，A 对各章进行数学、结果和论证审核，处理跨问依赖与矛盾，编写并整合完整论文，完成实际编译和逐页检查。

发现尚未满足题面要求时，A 继续求解；B 可以先写已确定部分，但必须登记缺失证据，不把“有可行解”“有所改善”当成“本问已完成”。不能派发没有来源的数值或让 B 代替 A 填补证明。

## A 给 B 的逐问派稿内容

沿用 [交接模板](交接/TEMPLATE.md)，任务编号采用 `QN-WRITE-rNN`；附上下面的信息。实际交接记录放在 `协作/交接/`，不在此另建模型或结果事实源。

A 的任务包中还须包含一段可复制到 B 会话的启动说明，写明角色、问题号、任务文件、证据版本、允许编辑的章节路径和交付标准。B 交 C、C 反馈 B 同样提供任务入口与准确版本。发起端不能代填接收端的“已开始”或“已验收”；未交接前只记录“待接收”。

| 项目 | 必须交代的内容 |
| --- | --- |
| 任务与版本 | 问题号、修订号、当前章节路径、输入与产物版本；已提交用真实 SHA，未提交则注明未提交并列文件 SHA-256，不拿 HEAD 冒充产物版本 |
| 题面要求 | 原题位置、需要回答的问题、输入、输出、硬约束和判定口径；已满足、未满足、未验证分别列出 |
| 论证主线 | 选择优化、机理、理论构造或混合模块；本问难点、模型选择理由、核心推导、求解路线、结果解释及局限 |
| 模型与证明 | 引用 `问题分析.md`、`建模报告.md` 的具体位置；统一模型名、变量、公式、假设和证明条件，说明继承与改动 |
| 结果证据 | 引用 `计算结果.md`、`图表/全部结果.json` 及相关 run-id、配置、校验记录；逐项给单位、精度和可陈述结论，禁止 B 使用旧结果 |
| 图表与资料 | 已核验图表路径及论点、数据来源、标题建议、必须引用的真实文献及定位；不要求机械凑图或模型 |
| 章节要求 | 具体小节顺序、需要展开的推导、可略写的标准方法、与上下问的接口；明确不可夸大的结论 |
| 格式与验收 | 当前官方文件、模板版本、交叉引用和图表约定；需交付的源稿、渲染页、写作卡及待解决项 |

正文使用 [逐问写作卡](写作核对/逐问写作卡模板.md) 和 [结果数值核对表](写作核对/结果数值核对表模板.md) 追踪。B 引用既有证据，不复制出另一套“最终结果”。

## A 统一规定的写作要求

- 正文围绕“本问任务与条件 → 数学模型或理论构造 → 求解或证明 → 结果检验与解释 → 本问回答”展开；可按实际任务合并小节，不固定每问字数或模型数量。
- 使用已修订的 [Word 主模板](../output/docx/02_2026华为杯AB题通用论文模板_修订版.docx) 与 [三类模块](../output/docx/03_2026华为杯三类逐问章节模块.docx) 作为结构参考；正式输出沿用项目选定路线，不让不同 Agent 混用 Word 和 LaTeX 源稿。当前项目为 XeLaTeX/PDF，具体交付文件路径由 A 派稿时指定。
- 格式以当届官方文件和正式题目要求为准。已存档的 2026 规范要求题目三号黑体、一级标题四号黑体居中、其他汉字小四宋体、单倍行距，无页眉，摘要页从 1 连续编号；摘要一般不超过两页，无需英文摘要。不得把历史页数、固定字数或独立目录当官方要求。
- B 交付完整学术段落、必要推导及正确的图表引用，不能只交大纲。模型与算法分开；独立问题不假装递进，继承问题不强造新模型。
- 明确区分数学证明、数值证据、经验解释和未验证推测；使用统一单位、有效数字与比较口径。已知失败、未达阈值及适用边界不得省略。
- 不把内部派稿、文件哈希、运行状态等协作字段直接堆入学术正文；复现信息归入合适的附录或支撑材料。
- 正文引用真实可追溯的来源。AI 辅助的实际使用记录及必要标注按当届规定落实，不由模板占位代替。

## C 的审查与返回格式

C 检查章节层级与模板一致性、字号行距、公式和符号排版、图表清晰度和单位、题注、自动编号、交叉引用、参考文献格式、断页、空白、溢出、匿名及占位残留。必须查看实际渲染；只有源稿时可以提供预审意见，但不能声称版式已通过。

每条意见包含：`问题号 / 章节修订号 / 问题ID / 文件与行号或PDF页码 / 发现 / 具体修改要求 / 阻塞或一般 / 接收人`。纯格式问题接收人为 B；涉及数学或结果时标为“待 A 核查”，不擅自判定已解决。

B 对每条意见返回修改位置、处理说明和新版本。C 的复查记录引用准确版本，并列出关闭项及未解决项；“未检查”不写成“通过”。默认 C 不重写章节，以免审查和作者职责混淆。

## 全部问题完成后 A 编写全文

A 逐问确认题面要求覆盖、模型及证明成立条件、结果与程序输出一致、检验口径完整，再检查跨问继承关系和联合结论。发现问题时返回自己的求解环节，或让 B 按明确要求修订。

A 统一术语、符号、模型名、文献、图表编号和章节衔接，编写或重写问题重述、共同假设与符号、必要的跨问讨论、结论、引用和附录；摘要与关键词最后根据当前有效全文编写。核心代码附录按当前源程序生成，不能使用过期摘录。

最后实际编译全文并逐页检查。C 的章节审查不能覆盖拼接后新出现的编号、分页、图表、引用或摘要数值问题，整篇论文仍由 A 负责终审。正式验收按项目 ASSURANCE 协议及真实人工复核要求执行。

## 三位操作者的交接与阶段边界

- 三位操作者各自在自己的 Agent 会话中执行 A/B/C 工作，不由 A 自动创建或启动 B/C，不把现有内部子 Agent 当作真人操作的 B/C。
- 默认使用独立 clone/worktree 和任务分支，通过任务文件、交接单、提交或 PR 传递成果。B 在自己的工作区写章节，C 在自己的工作区写审查记录；A 负责最终集成。若临时共用同一物理目录，先停止前一端写入并完成交接，再由下一端写入，禁止并发覆盖。
- A 指定 B 可修改的章节和附件范围；C 不直接修改被审章节。全篇入口、公共文献及跨问接口由 A 集成，代码和结果变更返回 A 处理。
- 人工接收、启动和反馈以实际记录为准，不假定另两端持续在线，也不声称后台自动传递消息。离线时按既有交接模板保留准确版本、未解决项和下一步。
- 逐问写作可提前产出草稿，但不改变七阶段顺序；进入 MANUSCRIPT 时必须依据当时有效证据重新确认草稿。上游模型、数据或结果变更后，A 标记受影响章节待更新并重走 B/C 审查。
- 交接状态只记录协作进度，不能替代 `状态/工作流状态.json`。正式阶段仍由 O 通过 `mm.py` 管理；本协议不修改固定技能或伪造 checkpoint。
