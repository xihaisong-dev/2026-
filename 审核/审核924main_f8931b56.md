## 2. 建模摘要

### 问题一

问题一把非 COPY 算子划分为子图，决定子图到核心的映射及每个核心上的顺序，目标按字典序最小化官方场景 A 评估器给出的 Makespan 和额外搬运量。`routes_gate_reuse` 使用有限候选、结构分量、通信/内存代理、局部路由和官方全局评估筛选方案；固定每图 `seed=0`、12 个评价槽位。加速比按每张图的固定整图单核官方核内启发式结果除以多核 Makespan，再对 100 张图逐比值取算术平均，并非总周期之比，也不是全局最优单核基线。

### 问题二

问题二调用未修改的官方场景 B 评估器，同核子图可在同一 Task 中保留 L1/UB 数据，跨核数据按官方 COPY 和同步延迟处理。`r07_reserve_fast` 以有限结构菜单、Q1 冻结迁移方案、场景 B 官方评估和有界局部修复搜索方案，局部生命周期与网络代理只用于候选排序，最终仍由官方 B Makespan 和额外搬运量决定。加速比分母是同一规定整图单核基线，不是问题一多核分数，也不是问题三 L2 基线。

## 3. 攻击清单

### 1. 严重：单核基线口径容易被写成“无优化基线”

- 位置：`问题一交付与赛题要求核对_r02.md:11`、`程序/q2_evaluator.py:43-46`。
- 攻击点：两问使用的是固定整图官方核内启发式单核基准，不是自行证明的无优化基准，也不是单核全局最优。
- 证据：Q1 文档明确采用 `S_k=(1/100)∑(T_i,1/T_i,k)`；Q2 代码的 `fixed_reference` 调用 `evaluate_singlecore`。
- 反例/边界：若单核启发式产生较差的核内 Pipe 顺序，而多核划分改变了核内顺序，单核分母偏大，5 核加速比可超过 5。
- 修复：正文统一称“规定整图单核基准”；另报单核基准方案、Makespan、核内规则，禁止写成“无优化单核”或“理论最优单核”。

### 2. 严重：5 核逐案例加速比超过 5，必须逐例解释

- 位置：`图表/runs/20260924-A-q1-delivery-r02/all_case_results.csv`、`图表/runs/20260924-A-q2-delivery-r07/selected_500_rows.csv`。
- 攻击点：Q1 最高约 `5.501`，Q2 最高约 `5.828`，Q2 有多例超过 5。
- 证据：Q1 文档也明确列出 `case_059` 五核 `5.501141`；Q2 数据中 `case_092` 五核约 `5.827795`，另有多例超过 5。
- 反例/边界：串行度高、单核启发式造成额外溢出或 Pipe 排布较差时，分母效应会放大加速比；若论文把它解释为“5 个同构核获得 5 倍以上物理加速”，则是错误结论。
- 修复：附录对全部超过 5 的案例列出单核/多核计划、Pipe 时间线、额外搬运和溢出字节，并做原官方评估器独立重放。

### 3. 严重：主结果的独立复现覆盖不足以替代全量新鲜重跑

- 位置：`审查/问题一交付与赛题要求核对_r02.md:53-57`、`审查/问题二r07计算提交与复现.md:12-13`。
- 攻击点：Q1 便携包抽样验证，Q2 便携包实际复现主要覆盖 case 001 单/双核和 case 005 五核；全量证据中的重放记录不能等同于本次在干净环境从输入重新生成全部 800 个最终结果。
- 证据：Q2 记录明确写“本机串行小测，无新增全量重算”；Q2 全量摘要记录 `fresh_B_final_replays=456`，但交付配置是 400 个多核配置，仍需说明这 456 的来源、对应方案和是否重新构造了当前入口。
- 反例/边界：官方评估器、Python 版本、输入配置或提交入口发生任一变化，保存的 evaluation JSON 仍可内部一致但不再代表当前入口结果。
- 修复：在干净解压目录执行全量 `q1_reproduce`、`q2_r07_reproduce`，保存命令、环境、源码/输入/配置哈希和每例官方结果哈希；至少对全部超过 5 倍案例做原官方 CLI 重放。

### 4. 严重：问题二把问题一方案作为首个候选，存在跨问公平性和披露风险

### 5. 中等：候选代理不是场景 B 的精确目标

- 位置：`程序/q2_physical.py:3-5`、`程序/q2_physical.py:55-71`、`程序/q2_physical.py:102-108`。

- 修复：论文将代理称为“候选排序指标”；提供代理排序与官方排序的固定候选对照，禁止把代理误写为完整 B 目标函数。

### 6. 中等：12 个评价槽位包含缓存命中和 padding，搜索质量不等于 12 个不同方案

- 位置：`程序/q2_current.py:16-31`、`程序/q2_current.py:74-80`、`程序/q2_current.py:85-89`。
- 攻击点：缓存命中仍计槽位是公平的，但候选菜单重复或不足时用 `J_padding_anchor` 补槽，实际独立候选数可能少于 12。
- 证据：代码显式为不足的局部提案填充 anchor，结果同时记录 `slots`、`official_calls` 和 `cache_hits`。
- 反例/边界：结构菜单大量重复的图上，算法可能只评估少量不同 B 方案，却与真正 12 个独立候选的结果并列比较。
- 修复：报告每图每核的唯一方案数、重复数、padding 数；补充“12 个独立合法候选”对照，或把预算口径写为“12 个评价机会”。

### 7. 中等：固定 `seed=0`，缺少随机稳健性证明

- 位置：`审查/问题一交付与赛题要求核对_r02.md:15`、`审查/问题二r07计算提交与复现.md:25-27`。
- 攻击点：Q1、Q2 当前正式结果均采用固定种子和固定预算，100 图是全量输入覆盖，不是多种子稳健性或独立留出验证。
- 证据：两份交付文档分别明确记录 `seed=0` 和每配置 12 个槽位。
- 反例/边界：结构菜单中存在随机 tie 或候选顺序时，seed 1/2 可能改变最终方案；仅报告 seed 0 无法说明结果对搜索随机性的稳定性。
- 修复：至少选结构分层的独立案例执行 seed 1/2/3 同预算复核，报告均值、标准差、最差退化和胜负数；不要用这些复核结果替换正式 seed 0 曲线。

### 8. 中等：不能把 400 组“13 胜 387 平”写成普遍算法收益

- 修复：正文同时报告胜/平/负、总周期、几何平均、额外搬运及最差案例，并明确 r07 是微小回归改进，不宣称显著普适收益。

## 4. 极端场景与验证要求

1. **全通信图**：每个生产者和消费者被放到不同核心，跨核 COPY 数量、500/1000 周期释放和共享 DDR 同时达到高压。应检查 `copy_in_start >= copy_in_release`、带宽竞争日志、最终 Makespan 和额外搬运是否均来自官方评估器，而非代理。
2. **关键路径极长图**：所有有效算子接近串行链。理论上增加核心不能显著降低关键路径；若加速比仍接近线性，应检查是否改变了算子、依赖或单核分母。当前仓库有部分链结构测试，但没有把该极端场景作为正式 Q1/Q2 结果单列。
3. **容量极小/高驻留图**：将配置副本的 L1/UB 容量压低，观察频繁 spill、无合法换出和跨核返回。该实验不能混入固定配置正式曲线；应验证代理不把“寿命面积下降”误认为“官方 Makespan 必然下降”。
4. **零通信独立分支图**：独立分量应允许并行，增加核心收益受 Pipe 工作量和核数限制；若结果出现异常超过核心数，应优先检查整图单核基准和任务构造。

- 未发现主分支直接改写官方场景 A/B 评估器的证据。

### 尚不能证明的事项

- 不能仅凭保存结果哈希证明全部 800 个最终结果都在当前主分支、当前机器上新鲜生成。
