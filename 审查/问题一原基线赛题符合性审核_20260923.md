# 问题一原基线赛题符合性审核

审核日期：2026-09-23。对象为第十八轮全100图实验的 `shared_region`，种子0、每次求解最多12个完整候选评价机会，2～5核共400组；不是主程序默认的旧 `alns`，也不是第十七轮实验增强组合。本次仅审查，不修改求解器、官方评估器、输入数据或已冻结结果。审查分支 `codex/q1-baseline-compliance-audit`。

**结论：原基线的场景A建模、方案可行性、官方数值结果、固定配置和平均加速比口径通过本次技术核验。尚不能宣称“全部赛题要求与提交材料均已满足”：全量运行没有证明所有用例稳定在5～10分钟内完成；现有入口、文件命名、代码清单和总结果登记仍有交付缺口。**

题面脚注原文是“以单个用例能在5 ~ 10分钟内给出结果为佳”，是效率目标，不能擅自改写为超过600秒即方案非法，也不能忽略实际超时记录。

## 二、逐项核验

| 题目要求 | 检查与结论 |
|---|---|
| 场景A：一个子图对应一个Task | 500份结果均为scene A；Task id与子图id一致，数量与方案一致；非COPY算子恰好执行一次。通过。 |
| 全部非COPY操作分配、无遗漏或重复 | 调用官方方案推导与任务顺序校验，并核对原始算子集和时间线。400/400通过。 |
| 子图DAG及多核执行不能死锁 | 官方校验同时检查数据依赖与同核串行顺序的联合图，而非仅检查子图DAG。400/400通过。 |
| 跨子图数据均经DDR，同核不得凭空驻留 | 官方Task构图对所有Task边界补搬运；本次按原始张量的生产/消费子图集合重新计数边界字节，与400份官方结果完全一致。计算不因同核映射而免除边界搬运。通过。 |
| 固定DDR总带宽及核内容量 | 保存结果全部为60 bytes/cycle、L1=524288、UB=131072；各核心保存的内存峰值不超过容量。官方源代码与附件一致。通过。 |
| 同核Task串行、跨核前驱等待 | 全量检查同核Task间隔至少100 cycles，跨核前驱完成后至少1000 cycles，任务内部操作时刻均在所属Task范围内。通过。 |
| 四条Pipe与数据依赖 | 按官方PIPE_SLOTS核对时间线并发上限；核对原始非COPY算子类别、Pipe、计算时长及生产者—消费者先后关系。通过。缓存复用依赖由未修改的官方调度器保证，未宣称独立重写验证了全部内存分配。 |
| Makespan优先，额外搬运次要 | 选择目标是官方 `(makespan, added_copy_bytes)` 的字典序，400份最终结果均等于该次候选历史最优二元组。搬运量按“调度后总量－原图总量”核对，并包含划分与溢出两部分。通过。 |
| 全部100个case、2～5核 | 每个case四种核数齐全，共400组，场景与参数一致；空闲核心允许存在，不要求强行使用所有核心。通过。 |
| 单核为整图核内启发式固定基准 | 使用官方evaluate_singlecore，将整图非COPY节点放进单一Task；四种核数共享相同分母。复用记录仅给单Task结果补空闲核，不赋予额外带宽。通过。 |
| 1～5核平均加速比 | 按100个逐case比值的算术平均，不是总时间之比；1核固定为1。通过。 |
| 避免暴力迭代搜索 | 有界贪心、最多3层粗化、每层最多32次接受收缩、固定4档划分与有限局部区域修复；外层最多12×80次提案尝试，最多12个完整评价机会。区域最多4个Task、512算子、6种划分变体×2种贪心顺序。没有枚举全部划分、核心组合或拓扑排列。符合有界启发式要求。 |

注意：`Cinner=Ccross`表示跨Task数据都经DDR的单位通信成本相同，**不表示两个等待参数必须相同**。附录B.4明确要求跨核前驱等待1000、同核Task切换等待100；现实现保留这种差异是正确的。

官方多核回放考虑共享DDR争用；代理成本不完全准确会影响候选质量，但最终成绩来自官方回放，不是把代理时长当作赛题结果。四个重新评估的样本提供额外核验，不能据此宣称已独立证明全部DDR事件模拟。

## 三、尚未满足或证据不足之处

### 1. 效率目标尚未获得全量冷启动保证

400次原基线求解的已记录搜索耗时中，有6次超过600秒：

| case | 核数 | 已记录秒数 |
|---|---:|---:|
| 014 | 3 | 1017.48 |
| 072 | 2 | 747.07 |
| 076 | 4 | 925.60 |
| 087 | 3 | 739.84 |
| 087 | 4 | 694.08 |
| 091 | 2 | 1019.25 |

另有5个整图单核参考的原始计算耗时超过600秒：014=950.13秒、028=679.32秒、072=1472.27秒、076=840.05秒、091=1690.45秒。最长约28.2分钟。不能拿复用基准时约1秒的读取耗时代替原始计算耗时。

这些数据混合不同机器、Python版本、并发负载、缓存和恢复来源，既不能据此断言任何机器上都达不到10分钟，也不能作为全量冷启动在10分钟以内的证明。目前只有候选数量预算，没有墙钟截止与提前返回机制。需要在指定环境、明确是否包含单核准备的口径下补做端到端计时；如果题目按单case整套核数考察，四种求解时间还需合计。

### 2. 入口默认算法与这条曲线不同

`程序/主程序.py` 默认执行旧 `alns`，必须加 `--experimental` 和7个特性才能复现本次原基线。实测以下命令在001/2核的方案、完整官方结果、12次候选评价轨迹与冻结结果一致：

```powershell
python 程序/主程序.py solve --cases case_001 --cores 2 --experimental --evaluation-budget 12 --seed 0 --features local_cost critical insertion comm_rank partition_guard shared_input region --output 图表/runs/20260923-A-q1-baseline-cli-reproduction
```

这是原型批处理入口，读取仓库processed中的case名称；尚未提供以任意输入图路径和核数为参数、直接输出比赛默认文件名的独立提交适配器。不能让接收者只运行默认命令并期待得到2.9907倍曲线。

### 3. 方案内容合法，提交命名和材料尚需整理

实验方案目前保存为 `plan.json` 或 `<case>_<k>cores_plan.json`，而附录B.5约定 `<case>_multicore_res.json`。顶层两个字段及内容已经通过官方验证；附录B.6也允许第二位置参数显式指定方案路径，所以这不是算法或JSON内容非法。

已用048/5核实际验证按规范文件名复制方案、调用官方CLI，结果为197613 cycles、额外搬运1716280 bytes，与原保存的完整结果一致（仅排除CLI新增的输入文件路径）。正式附件仍需为各核数分目录导出规范命名，并给出完整运行说明。

100图的折线图和900行实验CSV已经存在，但正式论文正文/逐case附录尚未完成集成；诊断图当前是英文标签，也尚未经过最终中文论文版式验收。本轮原基线附录应筛选100条单核基准与400条shared_region记录，不能把挑战者数据混入同一方案。

### 4. 代码与结果登记有陈旧项

`程序/code_manifest.json` 中 `q1_ablation.py` 与 `q1_experimental.py` 两项哈希落后于当前源码；`图表/全部结果.json`尚无followup_v18，README与计算结果入口仍以此前轮次为主。冻结运行自己的source_snapshot和结果哈希正确，因此不影响本次已核验数值，但会造成交付版本混淆。需在提交打包前更新清单、证据索引和说明，并固化提交版本。

正式工作流仍停留在研究准备状态，本次技术审查不代替正式门禁或人工验收。不需要因此重跑已通过校验的全部结果。

## 四、允许采用的结论与不应采用的表述

允许：在给定100图、固定参数、种子0和12个候选评价机会下，原基线400个多核方案通过检查，平均加速比分别为1、1.7003886008、2.2646970280、2.6855112751、2.9906610646。

不应表述为：所有用例都能10分钟内冷启动完成；默认入口即对应这条曲线；全部提交材料已经合规；算法达到全局最优；已经验证了所有随机种子或新图上的稳定性。

建议优先完成提交入口与命名导出、证据清单同步，然后专门解决大图端到端耗时。候选质量继续优化属于后续任务，不需要推翻当前合法的场景A模型。
